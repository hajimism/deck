テストの書き方

テストは、利用者に見えるもので要素を取り、表示と操作の結果を確かめれば、実装を直しても壊れず、本当の欠陥のときだけ落ちる

原則避ける書き方こう書くなぜ
利用者が知覚するもので要素を取るcontainer.querySelector(".btn-primary")クラス名 btn-primary の要素を探すscreen.getByRole("button",
{ name: "送信" })役割がボタンで、
読み上げられる名前が「送信」の要素を探す。
利用者やスクリーンリーダーと同じ見方		クラス名を変えても壊れない。
ラベルが消えたら気づける
実装の詳細ではなく、結果を確かめるexpect(state.isOpen).toBe(true)コンポーネント内部の変数を見るexpect(screen.getByRole("dialog")).toBeVisible()ダイアログが画面に見えているかを見る。
利用者が目にする結果そのもの		作り方を変えても、
利用者に見える結果が同じならテストは通る
非同期は、時間ではなく条件で待つawait sleep(1000)1秒待ってから確かめるawait screen.findByText("保存しました")「保存しました」が表示されるまで待ち、
表示されたらすぐ次へ進む		遅い環境でも落ちず、
速い環境で待ちすぎない
ネットワークは、境界で差し替えるAPI を呼ぶ関数を、テストごとに書き換えるMSW で、HTTP の応答を差し替えるアプリのコードをそのまま、
本番に近い形で試せる
状態ごとに Story を作る正常な表示の Story だけを作る読み込み中・成功・空・エラーの
Story を、それぞれ作る		操作テスト・見た目の回帰・アクセシビリティ監査を、同じ単位で回せる

テストが実装の詳細に依存すると、直すたびに無駄に落ち、本当の失敗がその中に埋もれる

用語：Testing Library＝利用者に見えるもの（ロール、ラベル、テキスト）で要素を取るテストの道具。test id＝テストのためだけに要素に付ける目印。MSW＝通信をその場で差し替える道具。Story＝Storybook で、部品を1つの状態で表示したもの

注：要素を取る優先順は、ロール → ラベル → テキスト → 最後に test id
