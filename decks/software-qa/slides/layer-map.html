欠陥の種類と検出段階の対応表

フロントエンドでは、欠陥の種類ごとに最も早く検出できる段階と道具が決まるので、チームでこの表を作れば、どこに何を置くかの基準になる

検出したい欠陥段階検出の方法代表的な道具
値の取り違え、規約違反予防型・lintTypeScript の strict、typescript-eslint、Biome
計算・変換・状態遷移の誤り自動テストユニットVitest、fast-check
コンポーネントの描画と操作自動テストコンポーネントTesting Library、Storybook、Vitest の Browser Mode
見た目の崩れ自動テスト見た目の回帰（VRT）Playwright の toHaveScreenshot、Chromatic、reg-suit
アクセシビリティ違反自動テスト自動監査＋手での確認axe-core、キーボードとスクリーンリーダーでの操作
API との食い違い自動テスト契約・結合OpenAPI から型とモックを生成、MSW
画面をまたぐ流れ、実環境の差自動テストE2EPlaywright
設計の誤り、認可やエラー処理の抜けレビュー人が読むPR のレビュー（境界・エラー処理・認可を毎回の観点にする）
仕様の漏れ、想定外の使い方探索探索的テストチャーター付きのセッション
性能の劣化自動テストCI での計測Lighthouse CI、バンドルサイズの上限
本番でしか起きない問題、利用者の環境での遅さ本番監視エラートラッキング、RUM、合成監視

手前の段階で検出できるものを、後ろの段階まで持ち越さない

用語：道具の名前は覚えなくてよい。Vitest＝JavaScript のテストを実行する道具。fast-check＝ランダムな入力を大量に作って試す道具。Storybook＝部品を状態ごとに表示する道具。Playwright＝ブラウザを自動で操作する道具。MSW＝通信をその場で差し替える道具。RUM＝実際の利用者の環境で速さを計測すること。合成監視＝決まった操作を定期的に自動で行い、本番が動いているかを見ること

注：上の行ほど手前の、早く気づける段階。axe-core などの自動監査で見つかるのはアクセシビリティの問題の一部で、手での確認は残る
