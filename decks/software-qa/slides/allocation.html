テストの配分（テスト戦略）

テストに割ける工数は限られているので、検出したい欠陥が多く、早く検出できる種類のテストに厚く割く。ピラミッドなどの形は、その配分の結果である

  1. テストピラミッド

    1. E2E
    2. 結合
    3. ユニット

    速いユニットテストを土台に厚くし、上に行くほど少なくする

    向く場面計算やルールの多いシステム

  2. テスティングトロフィー

    1. E2E
    2. 結合
    3. ユニット
    4. 静的解析

    静的解析を土台に、結合テストへ最も多く投資する

    向く場面画面が中心の JavaScript アプリ

  3. テスティングハニカム

    1. 統合済み
    2. 結合
    3. 実装の詳細

    サービスどうしをつなぐ結合テストを中心に置く

    向く場面多くのサービスに分かれたシステム

  4. アイスクリームコーン

    1. 手動
    2. E2E
    3. 結合
    4. ユニット

    手動と E2E に偏った、逆さの三角形

    向く場面避けるべき形

決め方① 保証する品質と検出したい欠陥を挙げる（問い1・2）　② それぞれを最も早く検出できる段階に割り当てる（対応表）　③ 棚卸しで漏れの多かった段階を厚くする

迷ったら最初の1本は、Testing Library のコンポーネントテストで書く。込み入った計算は関数に切り出してユニットに、画面をまたぐ流れだけを E2E にする

形から入らず、限られた工数を、検出したい欠陥が多いところに厚く割く

用語：テスト戦略＝限られた工数を、どの種類のテストにどれだけ割くかの方針。結合テスト＝部品どうしや、API とのつながりを確かめるテスト。静的解析＝コードを動かさずにツールで調べること。手動テスト＝人が画面を操作して確かめるテスト

注：形の違いの多くは、「ユニット」「結合」という言葉の定義の違いから来る。チームでは「検出する欠陥の種類」と「実行時間」で定義しておくと話がずれない。ピラミッドは Mike Cohn、トロフィーは Kent C. Dodds の提唱とされ、ハニカムは Spotify の技術ブログ（2018）で紹介された
