欠陥を作り込ませない設計

型で誤った状態を書けなくし、テストしやすいコードにしておけば、欠陥を作り込む余地そのものが減り、後ろの段階で探す手間も減る

型で、誤った状態を書けなくする

データの取得状態を真偽値と省略できる項目で表すと、ありえない組み合わせまで書けてしまう。状態ごとにデータの形を型で書き分けると、ありうる状態しか書けなくなる

書けてしまう

type State = {
  loading: boolean;
  data?: User;
  error?: string;
};

読み込みが終わったのに、データもエラーもない状態が書けてしまう

書けない

type State =
  | { status: "loading" }
  | { status: "success"; data: User }
  | { status: "error"; message: string };

「成功したのにデータがない」状態は、型エラーになって書けない

何を禁止するかを決めるのは人。守らせるのは型と lint で、違反は書いた瞬間に分かる

テストしやすいコードにする（テスト容易性）

  • 制御できる

    入力と状態を、外から与えられる

    時刻・乱数を引数で受け取る

  • 観測できる

    結果を、外から確かめられる

    ロールやラベルで要素を取れる UI にする

  • 分離できる

    依存を、差し替えられる

    fetch などの副作用を、差し替えやすい境界にまとめる

ロールやラベルで要素を取れる UI は、テストしやすく、同時にアクセシブルでもある

予防は、検出より前の段階で誤りを止める。後ろの段階で欠陥を探す手間そのものを減らすので、最も効く

用語：判別可能 union＝共通の項目（ここでは status）の値で、どの形かを区別できる型。副作用＝通信や時刻の読み取りなど、関数の外の世界に触れる処理。ロール＝ボタンや見出しなど、要素の役割を表す情報で、スクリーンリーダーなどの支援技術が読む
